# Brainstorm Gate — Containment Foreman

Date: 2026-11-04  
Status: gate passed; build scope intentionally limited to a reliable demo vertical slice.

## Product choice

Containment Foreman accepts a bounded coding/data task, creates a small execution plan,
dispatches each step to a disposable Docker sandbox, and returns an auditable receipt plus
small output artifacts. The demo story is: useful work is executed, but untrusted instructions
cannot escape the sandbox.

Primary demo task: create a summary from a supplied CSV and write a JSON artifact.  
Safety demo task: an injected instruction asks the worker to run `rm -rf /` and/or loop forever.

## Decisions

- Backend: Python standard library HTTP server, with a FastAPI-compatible shape avoided to keep
  the demo bootable on a fresh VM without dependency installation. The UI is server-rendered HTML.
- LLM adapter: OpenAI-compatible HTTP client using only `LLM_BASE_URL`, `LLM_API_KEY`, and
  `LLM_MODEL`; no provider name or key is embedded. If unavailable, a deterministic local planner
  is used so the safety path remains demoable.
- Execution: `docker run --rm` per step, `--network=none`, `--read-only`, bounded tmpfs/workspace,
  `--memory=512m`, `--cpus=0.5`, `--pids-limit=64`, `--cap-drop=ALL`,
  `no-new-privileges`, unprivileged UID, and a host-side timeout. No host mounts and no
  secret environment variables are passed to the container.
- Lifecycle: one container per step, always removed by `--rm`; temporary host staging is cleaned
  in a `finally` block. The runner refuses shell metacharacter-heavy or known destructive plans
  before dispatch, while still allowing the video to show defense-in-depth with a contained run.
- Receipt: exit code, status, duration, stdout/stderr SHA-256, and artifact metadata. Raw secrets
  and full untrusted output are not logged.
- Tests: verify no network, destructive command cannot touch a host sentinel, timeout is enforced,
  and sandbox env does not contain the host environment.
- Deployment: provide both a one-command Compose path and a reviewed cloud-init starter; the
  production/demo VM must keep `env.sh` root-owned and mode 600.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Docker unavailable locally | deterministic `--dry-run` mode and clear deployment check |
| LLM emits unsafe code | static plan gate plus Docker containment; never trust planner output |
| prompt injection in page/task text | treat task text as data; planner output is validated before execution |
| artifact exfiltration | no network, no host mounts, explicit output directory only |
| demo cannot prove safety | sentinel-file test and visible receipt with `network=none`, timeout, cleanup |
| Vultr provider wiring drifts | generic OpenAI-compatible env adapter; swap one base URL/model env |

## Out of scope for this submission

Real browser automation, multi-tenant auth, persistent queues, arbitrary file uploads, and
production-grade Kubernetes isolation. These are follow-up work, not claims in the demo.

## Acceptance gate

The implementation is ready for submission prep when: `pytest -q` passes; the UI can run one safe
task and one hostile/timeout task; receipts are reproducible; deployment docs show Vultr VM and
Serverless Inference env wiring; and the demo script explicitly captures the containment moment.
